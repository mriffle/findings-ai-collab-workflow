# CLAUDE.md — Findings Workflow (engine development)

This file governs work **on the plugin itself** (this repository). It is *not* the file that ships into a user's project — that one is generated by the init command from `templates/project-CLAUDE.md` and encodes the user-facing workflow behavior. Keep the two distinct.

## What this repository is

This repo is the **engine** of the Findings Workflow: a Claude Code plugin (agents, skills, commands, hooks, conventions, a vetted `lib/`, and universal defaults). It is also its own marketplace (`.claude-plugin/marketplace.json`).

The full design is in [`spec/`](spec/) (docs 01–08). **The spec is the source of truth for intent.** When code and spec disagree, the spec wins unless the spec is wrong about a verifiable external fact (e.g. the current Claude Code plugin format) — in which case fix the code to match reality and note the divergence.

## The load-bearing boundary (never blur it)

- **Plugin = engine.** Versioned, shared, identical for every user. Ships in this repo. Carries no study data.
- **User project = data + derived state.** The dataset, `state/`, `findings/`, `results/`, `figures/`, `research/`, `reports/`. Generated per dataset by the init command. Never lives in this repo.

If you find yourself putting study-specific data in the plugin, or re-implementing engine logic in a project, stop — the boundary is wrong.

## Architecture notes (durable)

- **The orchestrator is the main session, not a subagent.** It is governed by the user's project `CLAUDE.md` (materialized from `templates/project-CLAUDE.md` by `init`) plus the stage commands. There is deliberately **no `agents/orchestrator.md`** — the files in `agents/` are the *dispatched* workers the orchestrator calls.
- **Generator/reviewer pairing** is used wherever an artifact's correctness matters (code, stats, figures, research, reports): the reviewer checks the *artifact*, not the intent. The **verifier** is deliberately starved of conversation history (the clean context is the blind); the **findings-manager** is the sole writer of the findings graph + manifest.
- **Workflow progress and the integrity gate live in `state/workflow.json`** (in the user's project; schema in `conventions/workflow-state.md`). Commands update it; the `status` command renders it; `guard_findings.py` reads `.integrity_gate.passed` from it to gate finding writes (the *no-analysis-before-the-gate* ordering is carried by the `stage4-explore` command precondition + orchestrator behavior, **not** a hook — see `conventions/enforcement-map.md`). It is the one source of truth for "where are we in the pipeline."
- **Three distinct `CLAUDE.md` contexts:** this repo's root `CLAUDE.md` (engine dev) → never reaches users; `templates/project-CLAUDE.md` → the template; the user's project `CLAUDE.md` → written by `init`, auto-loads in their session. A plugin cannot auto-inject the third (current Claude Code behavior), which is why `init` writes it.

## Build conventions for the engine

- **Verify the plugin format against current Claude Code docs before writing manifests, hooks, agent/skill frontmatter, or commands.** The format shifts between releases (doc 08 version caveat). Don't build from memory.
- **Validate after changing plugin structure:** `claude plugin validate .`. Caveat: this validates the **marketplace manifest** (and resolves the plugin) — it does **not** deeply check component frontmatter. After editing `agents/`, `commands/`, or `skills/`, also parse-check their YAML frontmatter (each needs `name` + `description`).
- **Bump the plugin version on every release, or users get nothing.** `version` appears in **two** files that must agree — `.claude-plugin/plugin.json` (authoritative) and the `plugins[]` entry in `.claude-plugin/marketplace.json`. Claude Code gates updates on that string: an installed 0.2.0 against a marketplace 0.2.0 reports *"already at the latest version"* and pulls **no new code**, however many commits `main` is ahead. Bump both, then `claude plugin tag --push` (it validates the two agree and creates `findings-workflow--v<version>`). Do **not** hardcode the version anywhere else — `commands/init.md` writes it into a project's `findings/manifest.md` by *reading* `plugin.json`, so it can't go stale.
- **Reference bundled files with `${CLAUDE_PLUGIN_ROOT}`** (e.g. hook scripts, `lib/` modules) — never hard-coded absolute paths.
- **CI (`.github/workflows/ci.yml`) runs on push/PR — keep it green.** Three jobs: the hook guards (`hooks/test_guards.py` + ruff/`mypy --strict`) on **Linux/macOS/Windows** (the cross-platform safety net for the Python hooks); the `lib/` suite (ruff + `mypy --strict` + pytest, slow smoke tests deselected) on Python **3.11 + 3.12** — both interpreters the floor claims, via PEP 508 markers in `requirements-dev.txt` (scipy/xgboost have moved past 3.11, so that leg resolves older pins); and a cross-OS `claude plugin validate` + local-marketplace install (offline, no auth, no model driven). Engine dev/test deps are pinned in **`requirements-dev.txt`** (`pip install -r requirements-dev.txt` recreates the git-ignored `.venv`). No end-to-end model-driven hook-firing test (would need an API-key secret + tokens); the guard matrix + reviewer of Claude Code's documented hook semantics cover it instead.
- **File-format convention.** Use **Markdown (+ YAML frontmatter)** for everything LLM/human-maintained — findings, research, agents, skills, commands, conventions, **and the manifests/registries** (`findings/manifest.md`, `scripts/manifest.md`, `research/manifest.md`). Reserve **JSON** for files a **non-LLM parser** actually consumes: `state/workflow.json` (Python hook) and `state/color_registry.json` (Python plotting). Rationale: LLMs emit Markdown/YAML more reliably than JSON (no brace/comma fragility), and the consumer — not habit — decides the format. Each manifest is a *derived* index (source of truth = the underlying files / per-script `__script_meta__` headers), regenerable like the findings manifest.
- **A convention is only real if something checks it** (spec principle 9). Prefer a deterministic hook; otherwise a reviewer-agent check. Every rule in `conventions/` must map to an enforcer (the enforcement map, doc 05.5).
- **Keep hooks non-intrusive (preserve these invariants when editing `hooks/`):** the guards are **Python** (stdlib-only to run — no `bash`/`jq`), invoked in **exec form** via the project `./.venv` interpreter (two entries per guard, `.venv/bin/python` + `.venv/Scripts/python.exe`, so exactly one spawns per OS) so they run identically on Windows/macOS/Linux. Each guard **scopes to initialized projects** (`state/workflow.json` present) so it never touches unrelated repos, and **fails open** — on a malformed event, a missing project interpreter, or (promotion only) absent `ruff`/`mypy` — so it can't wedge a session. Block (exit 2) only on genuine violations. The promotion hook runs lint+types only — **tests are the code-reviewer's job**, since running tests synchronously in a tool-use hook is slow and unsafe. Run `python3 hooks/test_guards.py` (stdlib-only synthetic-event suite) after any guard change, and keep the guards `ruff`/`mypy --strict` clean; shared helpers live in `hooks/_hooklib.py`. See `hooks/README.md`.
- **`lib/` ships vetted *template scripts*, not a called library** (decision; see below): each template is held to the maximum (typed, tested, linted, seeds recorded) so it's a sound seed. Templates are copied into a project and adapted on demand; correctness is carried by the reviewer gates + template-lineage flagging, not by central propagation.
- **Python only** for analysis code (doc 05.2).

## Key implementation decisions (divergences & resolutions)

- **Shipping standing instructions to the user's project.** Plugins cannot auto-inject a project `CLAUDE.md` (current Claude Code behavior), which doc 08.6 assumed. Resolution: the **init command writes a project `CLAUDE.md`** (from `templates/project-CLAUDE.md`) into the user's working directory at setup; it then auto-loads as a normal project memory file. Must-fire rules are additionally backed by hooks.
- **Loader identifier fidelity — id columns are read as text (`wide-data-loader` v0.5 bugfix, 2026-09-01, from a user report).** `_read_wide` called `pd.read_csv` without a `dtype` for the id columns, so **pandas' type inference silently rewrote feature identifiers on the way in** — and the rewritten id lands in `Dataset.feature_names`, the key every downstream result, figure, and finding is reported against. Reproduced: `0001` → `1` (leading zeros dropped, and ids differing only in leading zeros **collide**), `1001` → `1001.0` (a *single* decimal value anywhere in the column promotes the whole column to float, so every id gains a `.0`), `1E5` → `100000.0`, `TRUE` → `True`, and an id spelling an NA token (`NA`) → the literal feature name `"nan"`. It hit `feature_names`, `feature_metadata`, **and** the precursor path's joined protein accessions. Sample-column headers were **not** affected (pandas keeps CSV header names as text), so pairing was never at risk — the damage was confined to feature ids. Two things make this unambiguously a defect rather than a scoping choice: the sibling `_load_metadata` already read `dtype=str` with the comment *"all columns str — no silent coercion"*, and `commands/stage3-loaders.md`'s verification checklist already requires *"Dtypes explicit and correct (no silent string↔numeric coercion)"* and *"Identifier integrity (no truncation/reformatting)"* — the template violated a rule the workflow itself mandates. Fix: `pd.read_csv(..., dtype={id_column: str})` (abundance columns still infer as numeric, and the precursor charge path still resolves ints via its existing fail-loud `pd.to_numeric`), plus a new `_check_ids_present` that **raises** on a missing/NA-token id instead of emitting the feature `"nan"`. The module docstring's "does not police domain fidelity" scoping was corrected: the loader still doesn't police corruption that arrived *in the file*, but it no longer *introduces* any. +8 planted-truth regression tests (`lib/tests/test_data_loading.py`, "identifier fidelity" section, raw-byte fixtures so the on-disk text is pinned). **Projects seeded from v0.4 or earlier carry the defect in their copied loader** — the template-lineage flag (`provenance.seeded_from.version`) is how such a project finds it; a re-load changes `feature_names`, so affected findings need re-verification.
- **How the orchestrator asks — one question at a time, options via `AskUserQuestion` (2026-09-01, user decision).** The workflow runs on the scientist's judgment and asks constantly (Stage 0's interview, the Stage 1 metadata + control-split checkpoints, Stage 2's preprocessing decisions, the Stage 3 integrity sign-off, Stage 4's model/enrichment checkpoints, Stage 6's mode + finding selection), but nothing governed *how*. The rule now: **one question at a time** (never a form dump — a batch gets one merged reply that silently drops half of it); when the answer is a **choice among known options**, **offer** them with **`AskUserQuestion`** and put the **recommended option first with its reason**; when the answer is genuinely open-ended, ask plainly in prose — **elicitation is prose, decisions are options** (the load-bearing nuance: Stage 0 is almost all elicitation, so without it the rule would push an interview into buttons); and **never ask what `state/`, the data, or the manifests already answer** (one-at-a-time only respects the scientist's time if each question needs them). Placement: the standing rule lives in **`templates/project-CLAUDE.md`** (new *How to ask* section) because the orchestrator is the **only** party that talks to the scientist — no `agents/` file interviews the user — and that file auto-loads every session, so it covers unscripted conversation too, not just the scripted checkpoints; a rule placed only in a command would lapse the moment the scientist just talks to Claude. The stage commands get **pointers, not restatements**, at the moments where they ask (`stage0` — plus a reconciliation of its ambiguous "one focused exchange, not a form dump" phrasing; `stage1`/`stage2`/`stage3`/`stage4`/`stage6`). Enforcer: **orchestrator behavior** (`conventions/enforcement-map.md` row + a note under *Human checkpoints*: a checkpoint folded into a multi-part question is not a checkpoint — the "yes" must attach to one thing). **No hook** — "was that two questions?" isn't decidable from a tool event, and a bad ask costs a merged answer, not a corrupt artifact. Also carried into `spec/02` §2.8. Noted in-rule: `AskUserQuestion` takes 2–4 options and is for *one* question with options, not a way to batch four questions into one dialog; where it isn't available, lay the options out in prose the same way (recommendation first).
- **Always leave the scientist with a next step — with a hard Stage-4 exception (2026-09-01, user decision).** The workflow is long and staged and its promise is that the scientist needn't memorize it, but nothing made the orchestrator *carry the thread*: Stages 0–3 each ended by naming the next stage and `status` already rendered "the single most useful next action", while **Stages 4, 5 and 6 ended on bookkeeping** and nothing at all governed the ordinary mid-conversation reply — which is where the complaint actually bit. The rule now: end a substantive response with **one concrete, named next step** (the command, the analysis, the finding id, the figure that would show a claim — *"we could explore further"* is not one); up to ~3 only when the path genuinely branches, and then as `AskUserQuestion` options with the recommendation first (composes with *How to ask*); at a boundary name the next stage command; **not after every message** (a footer on every reply is a nag — suggest at boundaries and whenever the scientist could reasonably not know what's next); and **suggestions are offers, not instructions** — the scientist's direction outranks them and a declined one is not raised again. **The Stage 4 exception is deliberate and hard** (the user's steer, and the option they picked over a softer "mention it once the picture looks mature" variant): Stage 4 is an open loop **only the scientist can close**, so suggest freely *within* it — the next analysis, a complementary method, a finding to record, a figure to commission, a script to promote, or **`stage5-validate <id>` on a matured candidate, which is a within-loop step, not an exit** (`stage4-explore.md` already says validation runs continuously as candidates mature) — but **never volunteer that exploration is over**: never raise `stage6-report`, never remark the findings look complete, never ask if they're ready to wrap up. Three reasons: exploration has **no end the agent can judge**; nudging toward closure is exactly the **motivated-reasoning pressure** Stage 0's own "Guard against motivated reasoning" and the phase-calibrated skepticism gates exist to resist; and the report's finding-selection is a **human checkpoint the scientist owns** (doc 02.8). Asked directly, answer plainly; signalled ("I think we have what we need"), follow — the rule forbids *raising* it, not discussing it. Placement mirrors *How to ask*: the standing rule in **`templates/project-CLAUDE.md`** (new *Leave the scientist with a next step* + the *Stage 4 exception* subsection) since it governs every response including unscripted conversation; the three gap stages get real endings (`stage4-explore` a *Where to next — and where not*, `stage5-validate` and `stage6-report` a `## Then`); `commands/status.md`'s next-action line is scoped so it never renders "next: write the report" (the pipeline diagram may still *show* Stage 6 — it's a dashboard, not a nudge); plus an `enforcement-map` row (**orchestrator behavior** — no hook can decide "was a next step warranted?") and `spec/02` §2.8.
- **Results first, null second for classifiers/regressors (2026-09-01, user decision).** The shuffle null was written up across the prose as a standing requirement — `skills/statistical-analysis/SKILL.md` said *"**Always** run a label-shuffle null … find it before reporting anything"*, `agents/stats-reviewer.md` required it *"present for classifiers"* — while the **template code already defaulted to `run_null=False`** and `conventions/statistics.md` already called it opt-in. So the engine contradicted itself, and the agent layer won: the scientist waited for the null before seeing anything. Measured at `classify` defaults (8 C × 6 l1_ratio grid, 5 folds × 5 repeats): nested CV ≈ **6,025** fits, the null (1000 permutations × 3 repeats × 5 folds, **fixed** hyperparameters — it does not re-tune) ≈ **15,000**, i.e. the null ≈ **2.5× everything else**, tripling the run. Resolution — a two-pass protocol: the **first pass runs without the null**, returning performance + coefficients/importances + figures fast; the result is stated as **not yet tested against a null** (finding capped `exploratory`, coefficients flagged), and the null is **proposed as the immediate follow-up** — *required before any strong claim, not optional garnish*, because it is also the **leakage detector**. **The stability loop stays in the first pass** (user's call, given the numbers): **50** fits ≈ **0.8%** of the run, and it carries the selection-frequency + resample-IQR trust read `conventions/findings.md` §2.3 demands beside every per-feature estimate; there is **no literal bootstrap** in the templates — the stability loop is the nearest thing. **No `lib/` change was needed** — this is a pure orchestration fix. The load-bearing edit is **`agents/stats-reviewer.md`**: without it the reviewer fails every null-free first pass and the change never takes effect; it now checks the *consequences* (marked `exploratory`, coefficients flagged, null recorded as the follow-up) and fails only if a strong claim rests on the untested result. Also wired: `agents/statistician.md` + `skills/statistical-analysis/SKILL.md` (the two-pass protocol), `conventions/{statistics,findings,enforcement-map}.md`, `templates/project-CLAUDE.md`, `spec/05`, and `commands/stage4-explore.md` — where the null **left the pre-run checkpoint** (four questions → three) and became a new *Results first, null second* section plus the **first entry** in the Stage-4 *Where to next* list, composing with the just-added next-step rule. The null run is a **new cached result** (different `run_null` param ⇒ different fingerprint), superseding the first, not a mutation of it. Boruta is exempt — its shadow features are a built-in null.
- **Per-agent model pinning — generator pinned to Sonnet, reviewer left on the default (`coder` 2026-07-13; `researcher` 2026-09-01, user decision).** Two agents name a model in their frontmatter (`model: sonnet`); every other agent omits the field. **Omitting it is not `inherit`** — per the current subagent docs, Claude Code resolves an unpinned subagent through its own order (per-invocation `model` parameter → the definition's frontmatter, where `inherit` explicitly selects the main conversation's model → the `CLAUDE_CODE_SUBAGENT_MODEL` env var → the main conversation's model); `inherit` is an available *value*, not the default. (The `coder` pin's commit message said "other agents remain on the default `inherit`" — same practical effect, imprecise wording; corrected here.) The pattern the two pins establish: **pin the generator of a generator/reviewer pair, leave the reviewer on the default.** `coder` is pinned while `code-reviewer` is not; `researcher` is now pinned while **`research-reviewer` is deliberately not** — the researcher does high-volume gathering across many sources, whereas the reviewer is the gate that verifies **every reference exists and supports the claim attributed to it**, and hallucinated or misattributed citations are the precise failure mode the research subsystem exists to stop (doc 04.5, the references invariant). The gates are where the engine spends its capability budget. Frontmatter format was re-verified against the live docs before the change, per the build convention (`model` accepts `sonnet`/`opus`/`haiku`/`fable`, a full model id, or `inherit`). The `agents/README.md` roster now carries a **Model column** so the pins are visible without opening each file.
- **Findings cross-reference each other by link — and the figure embed path was broken (2026-09-01, user decision + a bug found alongside it).** Findings had **no** convention for citing each other: `## Related findings` was defined as the narrative companion to the `relationships` edges but nothing said a mention should be navigable, and the only citation form in the engine was the report writer's `[F0042]`, which is a label, not a link. Now: **every mention of another finding in a body is a link** — target `<id>-<slug>.md` (findings are siblings in `findings/`), resolved from the manifest's `ID` + `Slug` columns, which is precisely what `Slug` was already documented to be for; **link text is free prose that must contain the zero-padded id**, so phrasing stays natural while the reference stays mechanically findable. **Links and edges are kept distinct** (`relationships` = the machine-readable graph; body links = human navigation): every edge target is narrated + linked in `## Related findings`, while a mention that is *not* an edge is **flagged as a possible missing edge, never invented** — the findings-manager proposes, the scientist types. **Unlike figure coverage this is cleanly decidable, so it is a hook**: `guard_findings.py` **invariant 5** blocks a full finding write where `finding NNNN` sits outside a markdown link targeting that id's file, deliberately narrow (the literal word `finding`/`findings` must precede the id; the document's own id is exempt) so a bare 4-digit year or sample count never trips it — +8 `test_guards.py` cases (**54 total**). Durability risk recorded: a link embeds the **slug**, so a rename breaks inbound links — `conventions/findings.md` §7 and the findings-manager's §E gain a **link-integrity pass** (repair from `ID`+`Slug`; a link to an `invalidated`/`superseded` target is **kept but flagged**, since the citation is part of the record). **Bug found while confirming the relative path:** `findings/` and `figures/` are **siblings** at project root, so the inline figure embeds shipped in the show-don't-tell change (`![…](figures/0042-volcano.png)`) resolved to `findings/figures/…` and **rendered as broken images in every viewer** — every figure that change made mandatory. Fixed to `../figures/…` across `conventions/findings.md`, `templates/finding.md`, and `agents/findings-manager.md`, with the underlying rule now stated explicitly: **frontmatter paths are project-root-relative** (scripts run from the root) while **body markdown links are `findings/`-relative**. The existing figure invariants were unaffected (they match basenames). Report citations were **deliberately left alone** (out of the requested scope; `reports/` sits at another directory level and would need its own relative path).
- **Stages advance on the scientist's word, not the orchestrator's (2026-09-01, user decision).** Checked first: the rule was **not codified anywhere**. Every stage command *named* the next stage (`## Then` → "Next: Stage 2 …") and nothing forbade simply starting it; the sole near-miss, `stage0`'s "Do not proceed to examine data", is an **ordering** rule (don't touch data before understanding), not a **permission** one. Worse, each `## Then` sets `current_stage: N+1` as bookkeeping, which reads easily as "we are in the next stage now, proceed." The rule now: finish the stage, report it, name what comes next, and **stop** — the scientist starts the next stage. **Permission** = running the stage command, asking in words, or a standing "keep going" instruction (a blanket request *is* a request, and it holds until withdrawn). **Not permission:** the orchestrator's own judgment that the prior stage looks complete, and — the subtle one — a **content sign-off**: a scientist confirming the metadata interpretation at the Stage 1 checkpoint has agreed *about the metadata*, not asked for Stage 2 to begin; they are different questions, so ask both or stop. **Bookkeeping ≠ advancing** (`<stage>_done` + `current_stage` record that the next stage is *available*). Scoped to **boundaries, not every step** — inside a stage the work is carried through without asking permission at each action, which is what keeps the rule from becoming obstructive. Placement mirrors the other two orchestrator rules: the standing rule in **`templates/project-CLAUDE.md`** (new *Stages advance on the scientist's word, not yours*, placed under *The absolute ordering rule* — that section says which stage may come next, this says who starts it), plus a **stop line at every stage boundary** (`stage0`–`stage6`, including `stage3`'s "unlocked is not started" — the integrity sign-off certified the *data*, it didn't ask for analysis to begin — and `stage4`'s "suggest these; don't start them" for `stage5-validate`). Enforcer: **orchestrator behavior + a human checkpoint at every boundary** (`conventions/enforcement-map.md` row + the Human-checkpoints table gains *Advance from one stage to the next*), carried into `spec/02` §2.8 (whose checkpoint table gains the same row). **No hook** — a tool event cannot distinguish a requested stage start from an unbidden one; the existing command preconditions catch only *out-of-order* starts, never a premature in-order one. Complements *Leave the scientist with a next step*: you suggest, they decide.

- **Shrinkage LDA as the third linear classifier — dual-form numerics, binary-only v0.1, triggered and compared paired against the elastic net (2026-09-17, user decisions; release 0.6.0).** The user asked for a shrinkage-LDA option. - **Linear-classifier selection rule tightened after a self-review (2026-09-17, user-approved; release 0.5.3).** Asked whether the 0.5.1 rule was accurate and appropriate, the review found four gaps and the user approved fixing them. **(1) Fold dependence:** the rule offered "a Wilcoxon signed-rank if a p is wanted" over the 25 per-fold differences of 5×5 repeated CV — but folds within a repeat share most training data and repeats reuse samples, so that p is **anti-conservative**. Now the per-fold differences + win/loss/tie counts are the primary evidence; a decisive p uses the **corrected resampled t-test** (Nadeau & Bengio 2003), or a Wilcoxon is labelled *indicative only*. **(2) Seed noise was a constant from one study:** the "±0.03 at n ≈ 40" band (measured on MagNet-EV) was presented as the tie threshold; the rule is now **sign consistency across a few seeds** (three as a reasonable minimum), with ±0.03 demoted to an example of scale. **(3) The tie-break invited motivated reasoning:** "settled by the reading the scientist needs" is correct in principle (the models answer different feature questions) but a reading chosen *after* both feature lists are visible picks the better story — so the reading (sparse minimal set vs dense module weights) is now **stated before the SVM runs** (Stage 4 asks it as one `AskUserQuestion`), and the stats-reviewer fails a tie settled post hoc. **(4) A comparison needs a cleanly tuned SVM:** the selection rule never linked to the SVM's `CGridEdgeWarning` / `TuningNoiseWarning`, so an elastic-net "win" could be an artifact of a grid that let tiny inner folds tune below the plateau; warnings are now resolved *before* comparing. Plus a minor one: picking the better of two models on the same nested CV is a selection step outside the CV (a small winner's-curse bias), so **both AUCs are reported**, not the winner's alone. Wired into `conventions/{statistics,enforcement-map}.md`, `agents/{stats-reviewer,statistician}.md`, `commands/stage4-explore.md`. Kept unchanged: elastic net first, the three triggers, paired evaluation on shared splits, "neither is the all-relevant answer", and the two-sided evidence.
- **Annotation concordance — the metadata is checked against the data at the integrity gate, conservatively (2026-09-17, user decision; release 0.5.2).** The Stage-3 pairing check was purely mechanical (every sample matched once *by key*), so a label swap or a mis-annotated animal upstream of the files passed it perfectly — silently and **common-mode** (the verifier reads the same metadata). The user asked for guidance that, where the data can speak to an annotation, it is asked — with a hard constraint: **never tell a scientist their metadata is wrong when it isn't; a flag only when it looks like a clear error.** So the conservatism is written into the rule, not left to judgment. **Eligible markers are near-binary only** (Y-linked proteins ↔ sex; a transgene / knockout product ↔ genotype; a protein drug ↔ arm; a strain/tissue marker); graded markers are out of scope. **Two steps, the second only if the first passes:** (1) the data must **prove the marker** — bimodal with a clear gap *and* the large majority of annotated samples on their expected side, else *the marker failed, not the metadata* → **inconclusive**, nothing flagged (the usual cause is a protein-group quantity carried by paralog-shared peptides → use unique peptides / precursor level); (2) only an **unambiguous** sample is flagged — squarely in the other mode, past the gap, consistent across technical replicates, and below a small flagged fraction (~a fifth; beyond it the marker is unreliable and the check reverts to inconclusive). **A flag is a question, default keep-as-annotated**; a correction is a **documented loader override or exclusion, never an edit to the hook-read-only metadata file**; a kept/excluded/overridden sample becomes a caveat finding, an inconclusive or concordant outcome records none; **every outcome is stated** (concordant / inconclusive / flagged / not checkable) so silence never reads as concordance. Placement mirrors the control-sample rule: Stage 1 **notes** the checkable annotations (prose elicitation — the scientist knows the transgene's name; touch no data), Stage 2 **confirms** the marker features are in the matrix and at which level, Stage 3 **runs** the check on the paired raw matrix over the experimental subset and shows a strip plot per annotation (`figures/qc/annotation-concordance/`, from-scratch, its own `figure-generator` family) at sign-off. Enforcer: **human checkpoint** (resolve a flag, one at a time, `AskUserQuestion`) + code-reviewer (the script) + figure-reviewer (the plot) + stats-reviewer (a gate-resolved annotation applied as the loader applies it; an inconclusive check is **not** a defect); **no hook** — a hook that could flag would flag too much, and over-flagging is the failure the rule exists to prevent. **Real-data basis (`testdata/5xFAD/`):** the human APP transgene `sp|P05067|5xFADA4_HUMAN` vs `Genotype` is bimodal with an empty log2 bin between modes, 68/74 experimental runs on their annotated side, and **8 discordant runs = 5 animals** (81/64/70 annotated 5xFAD but transgene-low in *both* replicates; 105/59 annotated WT/C57 but transgene-high) — meets the bar; DDX3Y/KDM5D vs `Gender` appear in females at male levels (shared peptides with DDX3X/KDM5C) — must come back **inconclusive**, and does. **Prose-only** — no `lib/` template, hook, or `workflow.json` field; an `annotation-concordance` template is queued in `QC_GAPS.md` with that oracle + counter-example. Wired across `commands/{stage1-metadata,stage2-data,stage3-loaders}.md`, `conventions/{correctness,enforcement-map,statistics,visualization}.md`, `agents/stats-reviewer.md`, `templates/project-CLAUDE.md`, `spec/{02,05}`, `QC_GAPS.md`.
- **Within-unit permutation for the label-shuffle null, and the tie-break settled by measurement (2026-09-14, user decisions; classifier templates → v0.3).** The three classifier templates' group-level null needed one label per unit, so a **batch-grouped design** (`generalization_target="batches"`, batches holding both classes) could never run a null and stayed `exploratory`. Now `classify` / `classify_xgboost` / `classify_svm` take **`null_permutation="units"|"within_units"`**: `units` (default, unchanged) hands each unit a new label as a whole — the null for a label that is a unit property; `within_units` shuffles labels **inside each unit, preserving per-unit class counts** — the restricted permutation for exchangeable blocks (Anderson & ter Braak 2003; Winkler et al. 2015), testing *label ⊥ proteome | batch*. Two verified facts made it clean: `StratifiedGroupKFold` assigns units to folds from their class counts, so under within-unit permutation the **grouped folds are byte-identical to the observed run** and only the labels move (pinned by a test); and on real 5xFAD (`groups="Cohort"`, cohort-held-out) the within-cohort null gives observed AUC 0.843 vs null 0.500 ± 0.098, p = 0.005 (slow smoke). Fail-loud guards, up-front: `within_units` needs grouped CV (else raise, naming the column); all units single-class → raise (the shuffle is the identity, p = 1 silently); fewer distinct arrangements (`∏ C(n_u,k_u)`, exact Python int) than `n_permutations` → `NullPermutationWarning`. The scheme applied is a **defaulted result field** (`null_permutation`: `samples`/`units`/`within_units`/`None`; pre-0.3 caches reload with the schema warning), named in the null figure's title, and a **fingerprint param**. The shared null block stays byte-identical across the three templates — `test_classification_splits.py` now checks it with `inspect.getsource`, alongside the CV-block invariant, which is untouched. Documented assumption: samples within a unit are exchangeable (a nested subject-within-batch design needs multi-level block permutation — not offered). **The `tie_break` option was *not* added:** a paired bake-off (same inner searches, both rules refit; MagNet 5 seeds + 5xFAD 3 seeds, 200 outer folds) found the held-out AUC identical in 90–99 % of folds, Wilcoxon p ≈ 0.75, per-seed swings −0.013…+0.020 = seed noise; where the rules differ the largest rule is the grid top in 128/135 folds — i.e. `c_grid=(1e6,)` by another name — and it would have falsified the upper-edge `CGridEdgeWarning` message and miscalibrated `n_folds_sub_plateau` (34 → 12). Evidence archived under the git-ignored `testdata/` preview dirs (`tiebreak_bakeoff.{py,csv}`); record in `FEATURE_FINDING.md` §B.1. Wired into `conventions/{statistics,results-cache}.md`, `commands/stage4-explore.md`, `agents/{statistician,stats-reviewer}.md`, `skills/statistical-analysis/SKILL.md`, `lib/manifest.md`.
- **Classifier review: the tuning-leak fix, the XGBoost grid scramble, fail-loud nulls, honest figures, measured null costs, and the paired comparison as a template (2026-09-17, user decisions; release 0.7.0).** A full review of the four classifier templates + figures + recommendation prose (independent per-template audits, each defect reproduced before it was fixed) found, in severity order: **(1) the inner tuning CV was never group-aware** — `classification` / `-svm` / `-xgboost` / `regression` built a row-level `StratifiedKFold`/`KFold` for `GridSearchCV` and never passed `groups`, even under a grouped outer CV, so a unit's replicates sat on both sides of a tuning fold: the tuning surface read AUC 1.000 on pure noise with technical replicates, the SVM's flat leaked curve pinned `C` to the grid floor and fired the *wrong* `CGridEdgeWarning`, and the tuning-free LDA was favoured artifactually in paired comparisons. Now a shared `_make_inner_cv` returns `StratifiedGroupKFold`/`GroupKFold` whenever the outer CV is grouped, `_check_inner_folds` refuses an unscorable inner fold, `groups[train]` is threaded through one `_tune` per template, and `inner_cv_grouped` is recorded (on the review's replicate design the grouped surface tops out at 0.64 / 0.69 / a negative R²). The outer estimate was always honest; the *hyperparameters* and the heatmap were not. **(2) XGBoost's tuning table was scrambled**: `mean_test_score` was reshaped `(n_depth, n_lr)` but `ParameterGrid` enumerates *sorted keys* with `max_depth` fastest, so the selected cell, the all-data model, the stability loop, the null, `best_params` and the heatmap all came from the wrong cell (7 of 8 runs disagreed with sklearn's own best; the elastic net and regression were right only because their key names happened to sort correctly). A shared `_grid_table` now indexes by the recorded `param_*` values and raises on a duplicate/unfilled cell; **every cached XGBoost result predates the fix and is mis-tuned**. **(3)** `select="smoothed"` was applied only to the all-data fit while the outer folds used GridSearchCV's argmax (the nested estimate evaluated a different rule than the reported model) — now `refit=False` + one `_select_cell` in every loop (the SVM's design), masking failed cells, refusing an all-NaN surface and a smoothed grid under three cells; the SVM's edge warning is keyed on the unsmoothed curve (3-point smoothing favoured edge picks). **(4)** pandas 3 keeps NA as a float through `astype(str)`, so the `labels != "nan"` sentinel was dead and a real empty metadata cell crashed every classifier — a shared `_labels_and_missing` masks with `isna()` first; a missing outcome is dropped, a missing *group* value raises (never a `"nan"` unit). **(5)** the null-path scorer had no single-class-fold guard and sklearn 1.9 returns NaN there, so a NaN observed AUC yielded `null_p = 1/(n_perm+1)` with `validated_eligible` true — the scorer raises, observed and every draw are checked finite, `cross_val_score(error_score="raise")`, and `n_permutations`/`null_repeats`/`n_splits`/`n_repeats`/`stability_repeats` are validated (0 permutations used to license a result). **(6)** `generalization_target="individuals"/"batches"` was accepted with `groups=None` and recorded — now refused. **(7)** LDA: balanced accuracy at score 0 was the *prior-shifted* operating point (not comparable with the siblings' `class_weight="balanced"`; minority recall 0.58 where the equal-prior cut gives 0.88) — **user decision: the equal-prior cut** (`equal_prior_cut_ = log π₊/π₋` of the training fold; scores unchanged); the ≥3-rows guard was false under grouped CV (a two-row class fitted silently with λ = 0) — `_fit_fold` refuses it; a near-constant within-class feature exploded a weight (42 vs sklearn's 1.77) — sklearn's `_is_constant_feature` bound. **(8)** XGBoost: **user decision: `importance_type` defaults to `total_gain`** (per-split average `gain` ranked single-split noise above stable signal: 1 of the top 8 planted vs 3);
