# CLAUDE.md — Findings Workflow (engine development)

This file governs work **on the plugin itself** (this repository). It is *not* the file that ships into a user's project — that one is generated by the init command from `templates/project-CLAUDE.md` and encodes the user-facing workflow behavior. Keep the two distinct.

## What this repository is

This repo is the **engine** of the Findings Workflow: a Claude Code plugin (agents, skills, commands, hooks, conventions, a vetted `lib/`, and universal defaults). It is also its own marketplace (`.claude-plugin/marketplace.json`).

The full design is in [`spec/`](spec/) (docs 01–08). **The spec is the source of truth for intent.** When code and spec disagree, the spec wins unless the spec is wrong about a verifiable external fact (e.g. the current Claude Code plugin format) — in which case fix the code to match reality and note the divergence.

## Current state

Everything in the layout below is implemented and committed on `main`. **`lib/` (the vetted template scripts, docs 04/06) is in progress:** the loader, normalization, batch-correction, and missing-value templates ship, plus the figure machinery (color registry + >8-category guard, dual-export/legend + publication style) and the seven QC/descriptive plot templates on it (PCA, CV, sample-correlation, abundance-boxplot, id-depth, missingness, dynamic-range), **and now the first analysis layer — the univariate differential-abundance family (`ols`/`moderated`/`welch`/`mannwhitney`) with its volcano + p-value-histogram result figures, the leakage-safe classifier (elastic-net logistic **classification** + its four result figures), **Boruta** all-relevant selection (`boruta_select` + its importance box-plot figure), and the leakage-safe **regression** (elastic-net linear `regress` — the continuous-outcome twin of the classifier + its four result figures)**; the analysis layer now ships in full. See **Next: building `lib/`** below. `claude plugin validate .` passes, and the engine was structurally reviewed end-to-end (no dangling references, consistent schemas, init dry-run + hooks all pass). See [`README.md`](README.md) for the component map and the per-directory `README.md` files for what each holds.

## The load-bearing boundary (never blur it)

- **Plugin = engine.** Versioned, shared, identical for every user. Ships in this repo. Carries no study data.
- **User project = data + derived state.** The dataset, `state/`, `findings/`, `results/`, `figures/`, `research/`, `reports/`. Generated per dataset by the init command. Never lives in this repo.

If you find yourself putting study-specific data in the plugin, or re-implementing engine logic in a project, stop — the boundary is wrong.

## Architecture notes (durable)

- **The orchestrator is the main session, not a subagent.** It is governed by the user's project `CLAUDE.md` (materialized from `templates/project-CLAUDE.md` by `init`) plus the stage commands. There is deliberately **no `agents/orchestrator.md`** — the files in `agents/` are the *dispatched* workers the orchestrator calls.
- **Generator/reviewer pairing** is used wherever an artifact's correctness matters (code, stats, figures, research, reports): the reviewer checks the *artifact*, not the intent. The **verifier** is deliberately starved of conversation history (the clean context is the blind); the **findings-manager** is the sole writer of the findings graph + manifest.
- **Workflow progress and the integrity gate live in `state/workflow.json`** (in the user's project; schema in `conventions/workflow-state.md`). Commands update it; the `status` command renders it; `guard_findings.py` reads `.integrity_gate.passed` from it to gate finding writes (the *no-analysis-before-the-gate* ordering is carried by the `stage4-explore` command precondition + orchestrator behavior, **not** a hook — see `conventions/enforcement-map.md`). It is the one source of truth for "where are we in the pipeline."
- **Three distinct `CLAUDE.md` contexts:** this repo's root `CLAUDE.md` (engine dev) → never reaches users; `templates/project-CLAUDE.md` → the template; the user's project `CLAUDE.md` → written by `init`, auto-loads in their session. A plugin cannot auto-inject the third (current Claude Code behavior), which is why `init` writes it.

## Build conventions for the engine

- **Verify the plugin format against current Claude Code docs before writing manifests, hooks, agent/skill frontmatter, or commands.** The format shifts between releases (doc 08 version caveat). Don't build from memory.
- **Validate after changing plugin structure:** `claude plugin validate .`. Caveat: this validates the **marketplace manifest** (and resolves the plugin) — it does **not** deeply check component frontmatter. After editing `agents/`, `commands/`, or `skills/`, also parse-check their YAML frontmatter (each needs `name` + `description`).
- **Reference bundled files with `${CLAUDE_PLUGIN_ROOT}`** (e.g. hook scripts, `lib/` modules) — never hard-coded absolute paths.
- **CI (`.github/workflows/ci.yml`) runs on push/PR — keep it green.** Three jobs: the hook guards (`hooks/test_guards.py` + ruff/`mypy --strict`) on **Linux/macOS/Windows** (the cross-platform safety net for the Python hooks); the `lib/` suite (ruff + `mypy --strict` + pytest, slow smoke tests deselected) on Python **3.11 + 3.12**; and a cross-OS `claude plugin validate` + local-marketplace install (offline, no auth, no model driven). Engine dev/test deps are pinned in **`requirements-dev.txt`** (`pip install -r requirements-dev.txt` recreates the git-ignored `.venv`). No end-to-end model-driven hook-firing test (would need an API-key secret + tokens); the guard matrix + reviewer of Claude Code's documented hook semantics cover it instead.
- **File-format convention.** Use **Markdown (+ YAML frontmatter)** for everything LLM/human-maintained — findings, research, agents, skills, commands, conventions, **and the manifests/registries** (`findings/manifest.md`, `scripts/manifest.md`, `research/manifest.md`). Reserve **JSON** for files a **non-LLM parser** actually consumes: `state/workflow.json` (Python hook) and `state/color_registry.json` (Python plotting). Rationale: LLMs emit Markdown/YAML more reliably than JSON (no brace/comma fragility), and the consumer — not habit — decides the format. Each manifest is a *derived* index (source of truth = the underlying files / per-script `__script_meta__` headers), regenerable like the findings manifest.
- **A convention is only real if something checks it** (spec principle 9). Prefer a deterministic hook; otherwise a reviewer-agent check. Every rule in `conventions/` must map to an enforcer (the enforcement map, doc 05.5).
- **Keep hooks non-intrusive (preserve these invariants when editing `hooks/`):** the guards are **Python** (stdlib-only to run — no `bash`/`jq`), invoked in **exec form** via the project `./.venv` interpreter (two entries per guard, `.venv/bin/python` + `.venv/Scripts/python.exe`, so exactly one spawns per OS) so they run identically on Windows/macOS/Linux. Each guard **scopes to initialized projects** (`state/workflow.json` present) so it never touches unrelated repos, and **fails open** — on a malformed event, a missing project interpreter, or (promotion only) absent `ruff`/`mypy` — so it can't wedge a session. Block (exit 2) only on genuine violations. The promotion hook runs lint+types only — **tests are the code-reviewer's job**, since running tests synchronously in a tool-use hook is slow and unsafe. Run `python3 hooks/test_guards.py` (stdlib-only synthetic-event suite) after any guard change, and keep the guards `ruff`/`mypy --strict` clean; shared helpers live in `hooks/_hooklib.py`. See `hooks/README.md`.
- **`lib/` ships vetted *template scripts*, not a called library** (decision; see below): each template is held to the maximum (typed, tested, linted, seeds recorded) so it's a sound seed. Templates are copied into a project and adapted on demand; correctness is carried by the reviewer gates + template-lineage flagging, not by central propagation.
- **Python only** for analysis code (doc 05.2).

**Done & committed** (`c4a0771` … `2a6c91a`): three `lib/common/` templates, each strict-typed + strict-linted + tested and registered in `lib/manifest.md`:
- **`wide-data-loader`** (`data_loading.py`) — study-agnostic fail-loud loader for wide feature×sample matrices + sample metadata. `load_wide_data` + `load_precursor_data` (vectorized charge collapse); orientation/pairing/duplicate-header/stripped-key/unique-feature guards, missing-value policy, zeros preserved. Returns the canonical `Dataset` tagged with a recorded `scale` (`linear`/`log2`/`log10`/`ln`/`glog2`/`zscore`/`ratio`).
- **`normalize`** (`normalize.py`, v0.4) — `Dataset`→`Dataset` median/MAD/VSN (pronoms) + `log2_transform` + **`to_linear`** (plain-log→linear inverse, `2**x`/`10**x`/`exp(x)`, strictly positive; refuses `glog2`/`zscore`/`ratio`/`linear`) + log-domain `median_center`; scale-tag guarded against the double-log trap; returns an independent (non-aliased) `Dataset`. `to_linear` (added 2026-07-13) exists to **de-log a ComBat-corrected matrix so a CV comparison is possible** — the batch-corrected CV state, since ComBat runs on log and `cv-plot` refuses log.
- **`batch-correct-combat`** (`batch_correct.py`) — ComBat (pycombat), **batch label only** (deliberate anti-cheat: never hand it the covariate of interest); log-scale guarded; near-constant-feature passthrough + finite backstop; `assess_batch_confounding` (bias-corrected Cramér's V, graded warning).

**Figure machinery (`lib/figures/`, shipped — same strict bar):** the color/figure foundation + the PCA, CV, sample-correlation, abundance-boxplot, id-depth, missingness, and dynamic-range plot templates. An independent 4-dimension subagent audit + remediation hardened these (bumped `okabe-ito-colors`→0.2, `figure-io`→0.3, `pca-plot`→0.3): the marginal-regression band now uses the residual-SE + t **mean-response CI** (was the slope SE × 1.96 — a too-narrow bug faithfully ported from the source `src/pca_plotting.py`, worth fixing there too); `plot_pca`/`save_figure` **never leak a figure on an error path** (close-on-every-exit); a ~0-variance (degenerate) PC's marginal regression is **skipped** rather than drawing an exploded slope; `load_palette` validates `max_categorical>=1` and clamps to distinct colors; `assign_colors` rejects reserved `_`-prefixed categories; the registry write is **atomic**; `base_name` rejects path separators cross-platform; PCA takes a recordable `random_state`.
- **`okabe-ito-colors`** (`colors.py`) — reads/extends `state/color_registry.json` (the nested project schema, *not* the source's flat one) so a `(category, value)` keeps one Okabe–Ito color across figures; deterministic next-unused assignment + persistence; gray background labels outside the palette; **raises `CategoricalPaletteExceededError` past 8 categories** — the deterministic >8-category guard.
- **`figure-io`** (`figure_io.py`) — `save_figure` **dual-exports** the figure (`<base>.{svg,png}`) plus an optional companion **legend image** (`<base>.legend.{svg,png}`) kept out of the plot so it can't overlap the data; `publication_style()` shared rcParams.
- **`pca-plot`** (`pca.py`) — `compute_pca`/`plot_pca`/`save_pca` on a `Dataset`: PC1/PC2 + PC3/PC4 panels with marginal KDE (categorical: Kruskal–Wallis/Mann–Whitney p) or regression (continuous: slope+p); standardized PCA; registry colors + >8 guard; greyable reference samples; **warns** (not refuses) on a non-log scale; renders a **separate legend image** (swatch key / colorbar). Generalized from the source `src/pca_plotting.py` (+ `plotting.py`, `colors.py`): we **kept** the source's separate-legend-image idea (legends overlap plots) but dropped its flat color registry + `tab10` fallback for our nested `state/color_registry.json` schema + >8 guard, and defaulted the continuous colormap to viridis. These ship the figure rows of `enforcement-map.md`/`visualization.md` (the dual-export, color-registry, and >8-guard *pending phase E* markers are retired). **Legend convention change:** the spec's `.legend.md` legend *document* (doc 06.3) is replaced by a legend *image* — the finding `figures[]` entry now carries `legend_png`/`legend_svg` + the existing free-text `caption` (see *Key implementation decisions*).
- **`cv-plot`** (`cv.py`, v0.1) — `compute_cv`/`plot_cv_distribution`/`save_cv` overlaying per-feature CV (`std/mean`) distributions for an ordered `{label: Dataset}` (histogram + Gaussian-KDE + annotated median lines). The canonical use is comparing **normalization states** (unnormalized/normalized/batch-corrected), the first QC plot built on the foundation: state colors via `okabe-ito-colors` (>8 guard free), dual-export + separate swatch legend via `figure-io.save_figure`. Generalized from source `src/cv_plotting.py` (which took raw arrays) to the `Dataset` contract; **upgraded the source's script-level MAD/VSN skip into a hard `CVScaleError` refuse on any non-linear scale** (`std/mean` is ill-defined where mean ≈ 0) — the deterministic enforcer, vs PCA's *warn*. Requires identical `feature_names` across overlaid states (n_samples may differ); `mean ≤ 0` → NaN (hardened over the source's `== 0`). Planted-truth + real-5xFAD smoke (median normalization drops the protein median CV 0.808 → 0.604). **Wired into the Stage 3 QC report (2026-06-26):** CV-by-normalization-state on the experimental subset (linear) + a **separate pool/control CV panel** (user decision) — `commands/stage3-loaders.md` QC step + `conventions/{statistics,visualization}.md`.
- **`sample-correlation`** (`correlation.py`, v0.1) — `compute_correlation`/`plot_sample_correlation`/`save_sample_correlation`: a hierarchically-clustered (scipy average linkage, drawn as a top dendrogram aligned to the heatmap via the `(icoord−5)/10` column map) **sample×sample** Pearson/Spearman correlation heatmap with caller-chosen metadata **annotation stripes** (categorical → registry colors + the >8 guard *per dimension*; continuous → viridis), the canonical *sanity check* — do experimental samples cohere, do controls self-cluster. Generalized from source `src/correlation_plotting.py` (which used `seaborn.clustermap`): **re-implemented on `scipy.cluster.hierarchy` + matplotlib — no seaborn, no new shipping dep** (user decision), for full layout control + clean separate-legend integration, consistent with `pca.py`. **Pearson on a non-log scale *warns*** (`CorrelationScaleWarning`: abundant-feature dominance drags r misleadingly low — verified on real 5xFAD, linear off-diag min 0.09 vs log2 0.62 vs Spearman 0.76), Spearman is rank/scale-invariant; correlation is defined on any scale so neither is refused (PCA-style *warn*, not CV's refuse) — user decision: default Pearson + warn, both methods as params. The r-colorbar stays on the figure (it's the data's value scale, unlike PCA's annotation colorbar) while the annotation keys are a separate legend image (a swatch block per categorical dim + a colorbar per continuous dim). **Controls are shown *with* experimentals**, distinguished by a Sample Type stripe — a documented divergence from "render controls separately", since the cross-class comparison is the deliverable. Planted-truth (an exact ±1 two-block matrix clustering must recover) + real-5xFAD smoke pinning the Pearson oracle (off-diag min 0.091 / median 0.896 / mean 0.823, n=61). **The annotation columns are wholly caller-chosen — nothing is baked in; default is no stripes.** **Wired into the Stage 3 QC report (2026-06-26)** as the design sanity check (controls shown *with* experimentals via the Sample Type stripe — the documented exception now carved into `conventions/visualization.md` + `spec/06.1` so the figure-reviewer treats it as conforming), and named as a **Stage 4 exploration seed** alongside PCA — `commands/{stage3-loaders,stage4-explore}.md` + `conventions/visualization.md`.
- **`abundance-boxplot`** (`abundance_boxplot.py`, v0.1) — `compute_sample_medians`/`plot_abundance_boxplots`/`save_abundance_boxplots`: a **stack of per-sample box plots**, one panel per processing state for an ordered `{label: Dataset}`, each box summarizing a sample's feature abundances. The canonical use is **raw → normalized → batch-corrected** read top-to-bottom (raw per-sample medians wander; normalization flattens them; batch correction removes residual shift) — the per-sample counterpart to `cv-plot`'s per-feature view. Generalized from source `src/abundance_boxplot_plotting.py` + `scripts/abundance_boxplot.py` (which made one figure per state on raw arrays) to the `Dataset` contract + a stacked multi-state comparison. Boxes colored by **column position** on a sequential colormap (default `cool`) — a position/ordinal encoding (no categorical budget consumed), so ordering samples by acquisition order upstream surfaces run-order drift (kept from the source). **Warns** (`AbundanceBoxplotScaleWarning`) on a non-log scale (PCA-style warn, not CV's refuse — a box plot is defined on any scale, just crushed on linear); per-panel y-labels derived from each state's `scale` tag (honest log2 vs glog2 vs zscore labels). Optional caller-chosen categorical (registry + >8 guard) / continuous (viridis) annotation stripes beneath the shared sample axis; legend (acquisition-order colorbar + annotation keys) is a separate image; figures never leak on an error path. Cross-state sample-alignment / empty-sample / 2D / annotation guards fail loud. Planted-truth (hand-computed per-sample medians) + real-5xFAD smoke pinning the oracle: median normalization **collapses** the per-sample median spread (std 1.04 → ~0, every sample to 20.6033). **Wired into the Stage 3 QC report (2026-06-26, with the user)** as the fourth QC template; abundance boxplots moved out of stage3's "no-template, write-from-scratch" list — `commands/stage3-loaders.md` QC step + `conventions/{visualization,statistics}.md` + `lib/manifest.md`.
- **`id-depth`** (`id_depth.py`, v0.1) — `compute_detection_counts`/`plot_id_depth`/`save_id_depth`: a **stack of per-sample bar charts**, one panel per feature level for an ordered `{label: Dataset}` (canonical: **protein over precursor**), each bar the count of *detected* features in a run (finite & `> min_intensity`; default 0). The most universal DIA QC view — it catches a failing/low-ID run or run-order drift (bars drawn in acquisition order) that an abundance summary smooths over. **No source oracle** (`src/sample_count_plotting.py` is the categorical sample-*count* chart, a different roadmap item) — designed fresh, reviewed by the user as a real-data preview first, then specced. ## Key implementation decisions (divergences & resolutions)

- **Shipping standing instructions to the user's project.** Plugins cannot auto-inject a project `CLAUDE.md` (current Claude Code behavior), which doc 08.6 assumed. Resolution: the **init command writes a project `CLAUDE.md`** (from `templates/project-CLAUDE.md`) into the user's working directory at setup; it then auto-loads as a normal project memory file. Must-fire rules are additionally backed by hooks.
- **The `validated` bar** (doc 03.2) is fixed as: **independent re-derivation (blinded analytic replication) + the phase bar** (exploratory vs confirmatory). Data replication is encouraged and recorded when available but is not mandatory for `validated`.
- **`lib/` is template scripts, not a called library** (diverges from doc 04.3, by design). Templates are copied into a project and adapted on demand (one analysis script per task); findings link to the project-local promoted script and record template lineage in `provenance.seeded_from`. Model + trade-offs in `lib/README.md`; governance in `conventions/script-registry.md`.
- **Manifests are Markdown; the file-format convention** (diverges from doc 03.7's JSON). Markdown(+frontmatter) for all LLM/human-maintained files incl. every manifest; JSON only where a non-LLM parser consumes it. Full statement under *Build conventions* above.
- **Figure legend is a separate image, not a `.legend.md` document** (diverges from doc 06.3, by user decision). A matplotlib legend baked into the axes routinely overlaps the data, so the legend is rendered as its own figure and dual-exported to `<base>.legend.{svg,png}` (`figure-io.save_figure` companion; `pca.save_pca` builds the swatch/colorbar). The finding `figures[]` entry carries `legend_png` + `legend_svg` (mirroring the figure's `png`/`svg` pair); the free-text figure caption uses the entry's existing `caption` field (which is what the `.legend.md` text role mostly duplicated). Reconciled across `conventions/visualization.md`, `findings.md`, `templates/finding.md`, and `enforcement-map.md`.
- **Script governance:** one analysis script per task (variations are parameters), reuse/DRY via shared `common/` modules (imported, never copy-pasted), per-script `__script_meta__` header as source of truth, `scripts/manifest.md` the derived index, **code-reviewer enforces** (no hook), and a promoted script imports only promoted modules. See `conventions/script-registry.md`.
- **Caveat findings — metadata imbalance/bias/confounding recorded as findings (`kind` field; 2026-06-25, by user decision).** The findings model gained a `kind: discovery | caveat` discriminator (default `discovery`, so back-compatible). A **caveat finding** records a structural property of the dataset/design — class imbalance, covariate skew, batch↔biology confounding — that constrains what downstream results can claim, distinct from an analysis-result *discovery*. Surfaced while **characterizing the cohort in Stage 1** (per-variable distributions, pairwise crosstabs, a publishable "Table 1"; descriptive-characterization rules + suggestive cutoffs in `conventions/statistics.md`), recorded `candidate`/`integrity_signoff: false` (legal pre-gate under `guard_findings.py`), with `integrity_signoff` flipped at the **Stage 3 integrity gate** — which is what *licenses* the caveat, since it certifies the sample↔metadata pairing the caveat rests on. Caveats carry descriptive evidence (no hypothesis test required), attach to the discoveries they qualify via a `relates_to` edge, drive downstream choices (confounded covariate → enters the model / stratify; imbalance → balanced metrics + stratified folds), and render as the report's **Limitations**. Trigger: record one when an imbalance/confound *would change how a downstream result is analyzed or interpreted* (judgment, not hard thresholds — record the consequential ones, not every histogram). No clean hook (a tool event can't decide "did you notice the imbalance?") — enforced by the Stage-1 human checkpoint + stats-reviewer (confounded contrast modelled, not ignored) + report-reviewer (caveats propagate). `kind` is wired through `conventions/findings.md` §2.6 (the definition), `templates/finding.md`, `conventions/manifest.md` (new `Kind` column), `agents/findings-manager.md`, `commands/{stage1-metadata,stage3-loaders,status}.md`, `conventions/{statistics,visualization,reporting}.md`, `templates/{project-CLAUDE,report}.md`, and `spec/02`+`spec/03`. Prose/spec only — **no `lib/` template** (a user's metadata schema is unknowable a priori).
- **Control samples (pools/references) detected in metadata understanding; experimental-only downstream (2026-06-25, by user decision).** Studies routinely mix experimental/biological samples with **control samples** — pooled QC, reference/bridge channels, standards, blanks — that must be viewed *separately* in QC and **excluded** from biological analysis. Stage 1 now **specifically hunts for controls** (preferring an explicit sample-role column like `sample type`/`type`/`class`/`role`, else inferring from naming conventions — Pool/QC/Ref/Bridge/Std/Blank — or from samples with no biological-group assignment) and classifies every sample **experimental vs control**. Two user decisions fix the shape: **(1) binary** classification (`experimental` vs `control`; the control *subtype* is noted in `state/METADATA.md` prose for QC, but the load-bearing distinction is binary, `experimental` = the analysis set); **(2) document-only** — the split + the rule deriving it live in `METADATA.md` as prose, **no canonical `sample_role` column and no change to the `lib/` `Dataset` contract** (same rationale as caveat findings: a user's metadata schema is unknowable a priori). Misclassification corrupts the analysis set both ways, so the inferred split is a **Stage-1 human checkpoint** and is **certified at the Stage-3 integrity gate** (carried onto the loaded samples, per-class counts reconciled) alongside the pairing. Downstream contract: biological analysis runs on the experimental subset, the exclusion is **recorded in `provenance.params`** (`sample_set`/experimental-n/excluded-control count), and QC renders controls separately (the QC-plot machinery itself is a future/phase-E session — only the standing rule is in place). No clean hook ("did you *find* the controls?" isn't decidable from a tool event) — enforced by the Stage-1 human checkpoint + integrity-gate sign-off + stats-reviewer (experimental-only + exclusion recorded) + figure-reviewer (controls rendered separately). Wired through `commands/{stage1-metadata,stage2-data,stage3-loaders}.md`, `conventions/{statistics,visualization,enforcement-map,findings}.md`, `templates/{project-CLAUDE,finding}.md`, and `spec/{02,05,06}`. **Prose/spec only — no `lib/` or hook changes.**
- **The integrity gate is not a single analysis-blocking hook** (divergence from doc 02/08 wording; spec annotated). As built: `guard_findings.py` hook-enforces only the *finding-write* side (no `integrity_signoff: true` / `validated` before `integrity_gate.passed`); the *no-Stage-4-analysis-before-the-gate* ordering is enforced by the `stage4-explore` command precondition + orchestrator behavior, because a single tool-use event can't cleanly distinguish exploratory analysis from legitimate Stage 3 loader/QC work (rationale in `conventions/enforcement-map.md`). The earlier "a hook blocks analysis" phrasing was inaccurate and has been corrected throughout.
- **Strict lint + types, and the `Dataset` contract (`lib/` build, 2026-06-23).** Analysis code is held to a **strict** bar: `ruff check` against an explicit strict ruleset + `mypy --strict`, plus `pytest` — codified in `conventions/coding.md`, seeded by `setup-env`'s generated `pyproject.toml`, enforced by `guard_promotion.py` (lint+types) and the code-reviewer (tests). For `lib/`, **the contract is the in-memory data structure, not the input file format**: a loader template returns a study-agnostic `Dataset` (abundances + feature ids + a row-aligned metadata table) so the downstream templates compose; the workflow writes a loader for whatever format a user actually has (never forcing one) but always targets that container. Details in the *Next: building `lib/`* section.
- **Hooks are Python, not bash (cross-platform; 2026-06-23).** The guards shipped as bash (`bash ${CLAUDE_PLUGIN_ROOT}/hooks/*.sh`, requiring `bash` + `jq` on `PATH`). Native Windows — now a first-class Claude Code platform — has neither, so a `command` hook is handed to PowerShell, `bash` isn't found, and the guard exits non-zero-non-2 ⇒ **every gate silently failed open on Windows** (the platform where enforcement should still hold). Resolution: the three guards are now **Python** (`guard_*.py` + shared `hooks/_hooklib.py`), stdlib-only to run (stdlib `json` replaces `jq`), wired in **exec form** via the project venv interpreter — two entries per guard (`.venv/bin/python` + `.venv/Scripts/python.exe`), mutually exclusive per OS so exactly one spawns; a missing path simply fails to spawn (fail open, non-blocking), with no double-run (Claude Code runs all hooks under a matcher in parallel). Python is already a hard dependency (`setup-env` ≥ 3.11), so this adds no new requirement; only `guard_promotion.py` shells out (to `ruff`/`mypy`, resolved `./.venv`-first). Trade-off (documented in `hooks/README.md`): the guards engage once the project env exists (post `setup-env`) — the gated artifacts (findings, promoted scripts) belong to Stage 3+ anyway, and the prior promotion guard already depended on `./.venv`. Logic ported faithfully (same regexes, lexical path-normalization, venv-first tool resolution, fail-open/scope rules) and locked by `hooks/test_guards.py` (29 synthetic-event cases; stdlib-only). Verify Claude Code hook semantics against current docs before changing the wiring (`${CLAUDE_PROJECT_DIR}`/`${CLAUDE_PLUGIN_ROOT}` expansion, exec vs shell form, parallel-run + spawn-failure-fails-open).
- **Project-local Python bootstrap (`setup-env`).** Floor is **Python ≥ 3.11**. The env is **project-local, zero global footprint**: interpreter + venv live under the project; setup never touches the user's `PATH`/profile. When no suitable Python exists, `setup-env` **transparently asks consent** before downloading `uv` + a standalone Python *into the project* (`UV_UNMANAGED_INSTALL` → `./.uv/bin`; `UV_PYTHON_INSTALL_DIR` → `./.uv/python`; `.venv` + `uv.lock` + `.python-version` committed, `.uv/`+`.venv/` git-ignored). The gate is a **`stage1-metadata` command precondition that live-verifies** the interpreter, **re-verified at the Stage 3 integrity gate** (not a hook — matches the stage-ordering pattern; only the `environment` block in `state/workflow.json` is recorded, advisory). The gate sits at **Stage 1, not Stage 3** (moved 2026-06-26, by user decision): Stage 1 is the first stage that *executes* Python — its metadata validity checks, cohort characterization (distributions/crosstabs/Table 1), and Cramér's V confounding statistics all run in code, so the "verified, not hand-asserted" understanding is impossible without an interpreter. The earlier "Stage 3 is the first stage that executes Python" framing was wrong and is retired across commands/spec/conventions/templates. Decline ⇒ user supplies Python themselves; Stage 1 stays blocked. `guard_promotion.py` was made **venv-aware** (resolves `ruff`/`mypy` from `./.venv` before `PATH`) so the project-local tooling actually powers the promotion gate. Verify uv flags against current docs before changing them.
- **Differential abundance is one template, four methods — not four templates (`lib/` build, 2026-06-29).** The univariate family (`ols`/`moderated`/`welch`/`mannwhitney`) ships as a single `differential_abundance(...)` entry with a swappable `method=`, because *the downstream is identical* — one `effect+CI+p+BH-q` table feeding one volcano + one p-value histogram (full rationale + the settled contrast API in `FEATURE_FINDING.md` §A.0b, decisions #2/#3/#5). Four deliberate calls vs the source oracle `feature_finding_ols.py`: **(1)** the per-study design-matrix *builders* are dropped — the template builds the treatment-contrast design internally from `contrast=`+`covariates=[…]` over `Dataset.metadata` (the named builders stay project-local, as do interactions until a v0.2 `formula=`); **(2)** the **CI gap is closed** — the oracle emits effect+p only, the convention requires effect+**CI**+corrected-p, so every method derives a CI (t / inflated-df-t / Welch-Satterthwaite / Hodges–Lehmann rank); **(3)** the oracle's silent `NaN→0` is **replaced by a hard raise** — missing handling is an upstream Stage-2 decision (`missing-values` template), so the test refuses NaN rather than zeroing (a constant feature is still left untestable: NaN p, excluded from BH, not an error); **(4)** non-log scale **warns** (effect is a log2FC; like PCA/correlation) rather than refusing. `welch`/`mannwhitney` reject `covariates=` (they cannot adjust) and a continuous contrast. The two result figures live in `lib/figures/` and depend on `analysis.differential_abundance` (the `*_from_result` bridges read the `DifferentialAbundanceResult`) — the first `figures/`→`analysis/` dependency, intentional. Validated by reproducing the oracle's OLS/moderated numbers exactly on real 5xFAD (the top disease hits are the canonical AD proteins). See `FEATURE_FINDING.md` and `lib/manifest.md`.
