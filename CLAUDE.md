# CLAUDE.md — Findings Workflow (engine development)

This file governs work **on the plugin itself** (this repository). It is *not* the file that ships into a user's project — that one is generated by the init command from `templates/project-CLAUDE.md` and encodes the user-facing workflow behavior. Keep the two distinct.

## What this repository is

This repo is the **engine** of the Findings Workflow: a Claude Code plugin (agents, skills, commands, hooks, conventions, a vetted `lib/`, and universal defaults). It is also its own marketplace (`.claude-plugin/marketplace.json`).

The full design is in [`spec/`](spec/) (docs 01–08). **The spec is the source of truth for intent.** When code and spec disagree, the spec wins unless the spec is wrong about a verifiable external fact (e.g. the current Claude Code plugin format) — in which case fix the code to match reality and note the divergence.

## Current state

Everything in the layout below is implemented and committed on `main`. **`lib/` (the vetted template scripts, docs 04/06) is in progress:** the loader, normalization, and batch-correction templates ship; the figure/color and analysis (differential abundance, classifier, regression) templates remain. See **Next: building `lib/`** below. `claude plugin validate .` passes, and the engine was structurally reviewed end-to-end (no dangling references, consistent schemas, init dry-run + hooks all pass). See [`README.md`](README.md) for the component map and the per-directory `README.md` files for what each holds.

## The load-bearing boundary (never blur it)

- **Plugin = engine.** Versioned, shared, identical for every user. Ships in this repo. Carries no study data.
- **User project = data + derived state.** The dataset, `state/`, `findings/`, `results/`, `figures/`, `research/`, `reports/`. Generated per dataset by the init command. Never lives in this repo.

If you find yourself putting study-specific data in the plugin, or re-implementing engine logic in a project, stop — the boundary is wrong.

## Architecture notes (durable)

- **The orchestrator is the main session, not a subagent.** It is governed by the user's project `CLAUDE.md` (materialized from `templates/project-CLAUDE.md` by `init`) plus the stage commands. There is deliberately **no `agents/orchestrator.md`** — the files in `agents/` are the *dispatched* workers the orchestrator calls.
- **Generator/reviewer pairing** is used wherever an artifact's correctness matters (code, stats, figures, research, reports): the reviewer checks the *artifact*, not the intent. The **verifier** is deliberately starved of conversation history (the clean context is the blind); the **findings-manager** is the sole writer of the findings graph + manifest.
- **Workflow progress and the integrity gate live in `state/workflow.json`** (in the user's project; schema in `conventions/workflow-state.md`). Commands update it; the `status` command renders it; `guard_findings.sh` reads `.integrity_gate.passed` from it to gate finding writes (the *no-analysis-before-the-gate* ordering is carried by the `stage4-explore` command precondition + orchestrator behavior, **not** a hook — see `conventions/enforcement-map.md`). It is the one source of truth for "where are we in the pipeline."
- **Three distinct `CLAUDE.md` contexts:** this repo's root `CLAUDE.md` (engine dev) → never reaches users; `templates/project-CLAUDE.md` → the template; the user's project `CLAUDE.md` → written by `init`, auto-loads in their session. A plugin cannot auto-inject the third (current Claude Code behavior), which is why `init` writes it.

## Build conventions for the engine

- **Verify the plugin format against current Claude Code docs before writing manifests, hooks, agent/skill frontmatter, or commands.** The format shifts between releases (doc 08 version caveat). Don't build from memory.
- **Validate after changing plugin structure:** `claude plugin validate .`. Caveat: this validates the **marketplace manifest** (and resolves the plugin) — it does **not** deeply check component frontmatter. After editing `agents/`, `commands/`, or `skills/`, also parse-check their YAML frontmatter (each needs `name` + `description`).
- **Reference bundled files with `${CLAUDE_PLUGIN_ROOT}`** (e.g. hook scripts, `lib/` modules) — never hard-coded absolute paths.
- **File-format convention.** Use **Markdown (+ YAML frontmatter)** for everything LLM/human-maintained — findings, research, agents, skills, commands, conventions, **and the manifests/registries** (`findings/manifest.md`, `scripts/manifest.md`, `research/manifest.md`). Reserve **JSON** for files a **non-LLM parser** actually consumes: `state/workflow.json` (bash/jq hook) and `state/color_registry.json` (Python plotting). Rationale: LLMs emit Markdown/YAML more reliably than JSON (no brace/comma fragility), and the consumer — not habit — decides the format. Each manifest is a *derived* index (source of truth = the underlying files / per-script `__script_meta__` headers), regenerable like the findings manifest.
- **A convention is only real if something checks it** (spec principle 9). Prefer a deterministic hook; otherwise a reviewer-agent check. Every rule in `conventions/` must map to an enforcer (the enforcement map, doc 05.5).
- **Keep hooks non-intrusive (preserve these invariants when editing `hooks/`):** each guard **scopes to initialized projects** (`state/workflow.json` present) so it never touches unrelated repos, and **fails open** if its tooling (`jq`/`ruff`/`mypy`) is missing so it can't wedge a session. Block (exit 2) only on genuine violations. The promotion hook runs lint+types only — **tests are the code-reviewer's job**, since running tests synchronously in a tool-use hook is slow and unsafe. Test guard changes against synthetic events before committing.
- **`lib/` ships vetted *template scripts*, not a called library** (decision; see below): each template is held to the maximum (typed, tested, linted, seeds recorded) so it's a sound seed. Templates are copied into a project and adapted on demand; correctness is carried by the reviewer gates + template-lineage flagging, not by central propagation.
- **Python only** for analysis code (doc 05.2).

## Next: building `lib/` (phase E, in progress) — start here if you're picking this up

Goal: add **vetted template scripts** that seed project-local analysis scripts and shared modules. Read first: `lib/README.md` (the model + contract), `lib/manifest.md` (what's shipped), `conventions/script-registry.md` (how project scripts are governed), and the memory `findings-workflow-build.md` (full session log incl. the loader design + the A–G hardening pass).

**Done & committed** (`c4a0771` … `2a6c91a`): three `lib/common/` templates, each strict-typed + strict-linted + tested and registered in `lib/manifest.md`:
- **`wide-data-loader`** (`data_loading.py`) — study-agnostic fail-loud loader for wide feature×sample matrices + sample metadata. `load_wide_data` + `load_precursor_data` (vectorized charge collapse); orientation/pairing/duplicate-header/stripped-key/unique-feature guards, missing-value policy, zeros preserved. Returns the canonical `Dataset` tagged with a recorded `scale` (`linear`/`log2`/`log10`/`ln`/`glog2`/`zscore`/`ratio`).
- **`normalize`** (`normalize.py`) — `Dataset`→`Dataset` median/MAD/VSN (pronoms) + `log2_transform` + log-domain `median_center`; scale-tag guarded against the double-log trap; returns an independent (non-aliased) `Dataset`.
- **`batch-correct-combat`** (`batch_correct.py`) — ComBat (pycombat), **batch label only** (deliberate anti-cheat: never hand it the covariate of interest); log-scale guarded; near-constant-feature passthrough + finite backstop; `assess_batch_confounding` (bias-corrected Cramér's V, graded warning).

Wired into the workflow: stage2 (record scale; confirm normalization / batch axis+confound / missing-value handling), stage3 (QC normalizes + surfaces confounding, does **not** correct), stage4 (correction-as-analysis: assess→sign-off→both-ways; prefer batch-as-covariate for *testing*), plus `conventions/statistics.md` + `enforcement-map.md` and `templates/finding.md` provenance. Baseline deps `pronoms==0.4.0` + `pycombat==0.20` added to `setup-env`. **78 tests**; an adversarial 4-dimension audit hardened the ComBat zero-variance logic, a confounding NaN-drop, `Dataset` aliasing in the transforms, and Cramér's-V small-n bias. **Missing-value handling is a scientist decision surfaced in Stage 2** (leave 0 / impute mean·median or KNN / drop), not a template — by decision.

**The earlier open questions are now settled:**
- **Layout:** `lib/common/` = shared modules (seed the project's `scripts/promoted/common/`); `lib/tests/` = the maximum-bar tests; `lib/manifest.md` = the derived registry. Add `lib/analysis/` and `lib/figures/` for entry-point templates as they come.
- **Versioning:** a `template: {name, version}` block in each script's `__script_meta__` header is the source of truth; `lib/manifest.md` indexes it; a finding's `provenance.seeded_from` references name+version. `0.x` pre-first-use; bump minor on a logic/signature change.
- **The canonical contract = the `Dataset` structure** (abundances ndarray `(n_samples, n_features)` + `feature_names` + `feature_metadata` + a row-aligned metadata `DataFrame`). Downstream templates consume `Dataset`; **the contract is the data structure, not the input file format.**

**User's standing guidance (durable — honor it):**
- **Never force a user's data format.** The workflow examines the data/metadata, confirms structure with the scientist (Stages 1–2), and writes a tested loader for *their* files using the template as a guide; format details are arguments, not assumptions.
- **Every loader returns the standard container** so the other templates compose unchanged. *Adapt the input; keep the output structure.*
- **Strip dataset-specific exceptions** out of templates — sample exclusions, relabelings, identity corrections live in the project copy, **never** the template.
- **Testing is paramount** (already codified in `conventions/coding.md` + the reviewer gates — do **not** re-add language).

Root `pyproject.toml` carries the **strict bar** (`mypy --strict` + the strict ruff ruleset, mirroring `setup-env`) plus pytest config (`pythonpath=["lib"]` so tests import `from common import …` exactly as a project would; `mypy_path="lib"`). ## Key implementation decisions (divergences & resolutions)

- **Shipping standing instructions to the user's project.** Plugins cannot auto-inject a project `CLAUDE.md` (current Claude Code behavior), which doc 08.6 assumed. Resolution: the **init command writes a project `CLAUDE.md`** (from `templates/project-CLAUDE.md`) into the user's working directory at setup; it then auto-loads as a normal project memory file. Must-fire rules are additionally backed by hooks.
- **The `validated` bar** (doc 03.2) is fixed as: **independent re-derivation (blinded analytic replication) + the phase bar** (exploratory vs confirmatory). Data replication is encouraged and recorded when available but is not mandatory for `validated`.
- **`lib/` is template scripts, not a called library** (diverges from doc 04.3, by design). Templates are copied into a project and adapted on demand (one analysis script per task); findings link to the project-local promoted script and record template lineage in `provenance.seeded_from`. Model + trade-offs in `lib/README.md`; governance in `conventions/script-registry.md`.
- **Manifests are Markdown; the file-format convention** (diverges from doc 03.7's JSON). Markdown(+frontmatter) for all LLM/human-maintained files incl. every manifest; JSON only where a non-LLM parser consumes it. Full statement under *Build conventions* above.
- **Script governance:** one analysis script per task (variations are parameters), reuse/DRY via shared `common/` modules (imported, never copy-pasted), per-script `__script_meta__` header as source of truth, `scripts/manifest.md` the derived index, **code-reviewer enforces** (no hook), and a promoted script imports only promoted modules. See `conventions/script-registry.md`.
- **The integrity gate is not a single analysis-blocking hook** (divergence from doc 02/08 wording; spec annotated). As built: `guard_findings.sh` hook-enforces only the *finding-write* side (no `integrity_signoff: true` / `validated` before `integrity_gate.passed`); the *no-Stage-4-analysis-before-the-gate* ordering is enforced by the `stage4-explore` command precondition + orchestrator behavior, because a single tool-use event can't cleanly distinguish exploratory analysis from legitimate Stage 3 loader/QC work (rationale in `conventions/enforcement-map.md`). The earlier "a hook blocks analysis" phrasing was inaccurate and has been corrected throughout.
- **Strict lint + types, and the `Dataset` contract (`lib/` build, 2026-06-23).** Analysis code is held to a **strict** bar: `ruff check` against an explicit strict ruleset + `mypy --strict`, plus `pytest` — codified in `conventions/coding.md`, seeded by `setup-env`'s generated `pyproject.toml`, enforced by `guard_promotion.sh` (lint+types) and the code-reviewer (tests). For `lib/`, **the contract is the in-memory data structure, not the input file format**: a loader template returns a study-agnostic `Dataset` (abundances + feature ids + a row-aligned metadata table) so the downstream templates compose; the workflow writes a loader for whatever format a user actually has (never forcing one) but always targets that container. Details in the *Next: building `lib/`* section.
- **Project-local Python bootstrap (`setup-env`).** Floor is **Python ≥ 3.11**. The env is **project-local, zero global footprint**: interpreter + venv live under the project; setup never touches the user's `PATH`/profile. When no suitable Python exists, `setup-env` **transparently asks consent** before downloading `uv` + a standalone Python *into the project* (`UV_UNMANAGED_INSTALL` → `./.uv/bin`; `UV_PYTHON_INSTALL_DIR` → `./.uv/python`; `.venv` + `uv.lock` + `.python-version` committed, `.uv/`+`.venv/` git-ignored). The gate is a **stage-3 command precondition that live-verifies** the interpreter (not a hook — matches the stage-ordering pattern; only the `environment` block in `state/workflow.json` is recorded, advisory). Decline ⇒ user supplies Python themselves; Stage 3 stays blocked. `guard_promotion.sh` was made **venv-aware** (resolves `ruff`/`mypy` from `./.venv` before `PATH`) so the project-local tooling actually powers the promotion gate. Verify uv flags against current docs before changing them.
