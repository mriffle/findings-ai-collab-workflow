# Stage 4 — Explore ⇄ record findings  (the heart)

**Precondition (hard):** `state/workflow.json` shows `integrity_gate.passed: true`. **If it is not true, refuse** — no analysis before the integrity gate passes (doc 02.3). Tell the scientist to complete `stage3-loaders`. (This ordering is enforced by *this precondition* + orchestrator behavior; `guard_findings.py` additionally blocks any finding that claims sign-off / `validated` before the gate.)

This is the open loop the whole system exists to capture. With understanding established and the read verified, explore the data *with* the scientist and turn insight into durable findings.

## The loop

1. **Spark discussion with vetted boilerplate.** Seed standard analyses (differential abundance via moderated models, nonparametric tests, feature finding, leakage-safe classifiers, regression, dimensionality reduction) to give the scientist something to react to — **from a `lib/` template where one exists** (copy it into `scripts/scratch/` and adapt), otherwise write the analysis from scratch against `conventions/statistics.md` + `conventions/coding.md`, or reuse the project's existing script for that analysis (one script per task). Starting from a vetted template beats generating fresh statistics code; models get assumptions and missingness handling wrong in ways that look fine. The **`pca-plot` and `sample-correlation`** figures from the Stage 3 QC report recur here as natural exploration seeds — now read for *biology* rather than QC (e.g. PCA colored by the variable of interest, correlation annotated by the contrast), on the normalized log data. The **`dynamic-range`** plot likewise recurs: re-render it with `highlight_features` populated — the study's **domain / hypothesis proteins of interest** and/or the **top differential-abundance hits** (optionally split into `highlight_groups`, e.g. contaminant vs of-interest) — turning the QC dynamic-range curve into a results figure that shows *where the proteins of interest sit in the dynamic range* (a low-abundance target quantified near the noise floor is a real caveat worth recording). Offer this re-render once proteins of interest are ascertainable. The **univariate differential-abundance** family now ships as a template: seed from **`lib/analysis/differential-abundance`** (`differential_abundance(dataset, contrast=…, covariates=[…], method="moderated")` — `moderated` default, also `ols`/`welch`/`mannwhitney`), which returns the per-feature **effect+CI+p+BH-q** table; render it with **`lib/figures/volcano`** (`volcano_from_result`) and **`lib/figures/pvalue-hist`** (the calibration check — and the overlay for the both-ways corrected/uncorrected comparison). The **classification** question — *can the proteome predict the class?* — now ships too: seed from **`lib/analysis/classification`** (`classify(dataset, outcome=…, binarize=…, run_null=…)`), whose coefficients are a **caveated interpretation** of a minimal-optimal predictor (**not** an all-relevant selection — that is Boruta; a low selection frequency ≠ unimportant), rendered with **`lib/figures/classification`** (ROC-vs-null, coefficient/selection-frequency, hyperparameter heatmap). When the class boundary may be **non-linear or interaction-driven**, offer the **tree** sibling *alongside* (not instead of) the linear one: seed from **`lib/analysis/classification-xgboost`** (`classify_xgboost(dataset, outcome=…, binarize=…, run_null=…)`, gradient-boosted trees — the **same** nested-CV + stability + opt-in label-shuffle-null shape), rendered with **`lib/figures/classification_xgboost`** (ROC-vs-null, **importance**/selection-frequency, max_depth × learning_rate heatmap). Its **gain importances are unsigned** (a magnitude, no direction — no sign consistency), and it is **scale-invariant** so it neither standardizes nor warns on a non-log scale; it is more overfit-prone on small-n and harder to interpret causally, so read it against the linear model (a feature both flag is robust; the tree is the one to reach for when a linear boundary underperforms). It still **raises on NaN** and takes the same Stage-4 checkpoint below. Before running it, settle four things with the scientist (a **Stage-4 checkpoint**) — **one at a time**, each as an `AskUserQuestion` with the recommended option first where it is a choice (*How to ask*, project `CLAUDE.md`), never as a four-part question: the **generalization target** (unseen samples / individuals / batches → the CV fold unit); whether the independent unit (`groups=`) **actually repeats** (group only if so — else row-level *is* individual-level); that **missing values are resolved** upstream (the classifier raises on NaN); and whether to pay for the **label-shuffle null** (`run_null=True` is opt-in — running it lets the finding reach `validated`, skipping caps it at `exploratory`). Also surface any **consequential** outcome↔covariate confound (a Stage-1 caveat, gated by consequence — *not* every imbalance) in plain language and decide together whether to address it. The **all-relevant** question — *which features are all jointly relevant?* — is **Boruta's**, the complement to the classifier's minimal-optimal set: seed from **`lib/analysis/boruta`** (`boruta_select(dataset, target=…)` — task inferred from the target dtype, regression or multiclass-native classification), rendered with **`lib/figures/boruta_importance`** (per-iteration importance vs the shadow noise floor). Boruta is **structurally simpler** than the classifier — its shadow features are a **built-in null**, so it needs no `run_null` and no CV, running **once on the whole experimental matrix** (feeding it the ComBat-corrected matrix is legitimate here — this is selection, not a per-feature test). Two Stage-4 notes: it is **minutes-slow** on a real scope, so **cache the result** and re-render figures from the cache (see *Caching heavy results* below — `conventions/results-cache.md`); and running Boruta **alongside** the classifier is the honest read — a feature the classifier zeroed but Boruta confirms is redundant-but-real (a correlated neighbour), not noise. **Tuning when the default run lands badly** (a legitimate, *recorded* adjustment — the tuned knobs enter `provenance.params` and the cache fingerprint, since they change the selection): if **too few features Confirm**, raise `max_iter` (try `200`, so borderline Tentatives get more iterations to resolve) and/or **lower** `perc` toward `95` or `90` (a more lenient shadow noise floor more real features clear); if the Confirmed set is **too large for a tractable downstream analysis**, lower `alpha` to `0.01` (from the `0.05` default — a stricter accept/reject bar that confirms fewer, higher-confidence features). The **continuous** analogue — *can the proteome predict a continuous outcome (dose, time, age), and how well?* — is the **regression** template: seed from **`lib/analysis/regression`** (`regress(dataset, outcome=…, groups=…, run_null=…)`, elastic-net linear — the **same** nested-CV + coefficient/stability + opt-in **target**-shuffle-null shape as the classifier, reporting **R²/RMSE/MAE**), rendered with **`lib/figures/regression`** (predicted-vs-observed scatter, target-shuffle null, coefficient/selection-frequency, hyperparameter heatmap). Settle the same Stage-4 checkpoint as the classifier (generalization target; whether `groups=` **actually repeats**; missing values resolved — `regress` raises on NaN; opt-in `run_null=True`); the outcome must be **numeric** (a categorical outcome is the classification path — `regress` raises otherwise). For **all three predictive templates** — the elastic-net classifier (`classify`), the tree classifier (`classify_xgboost`), and the regressor (`regress`) — offer the scientist an optional restriction to a **curated / hypothesis-driven feature list** (`feature_list=` — domain proteins of interest, e.g. a published panel) *alongside* the whole-proteome run: it cuts dimensionality (`p >> n`), can sharpen a weak signal, and aids interpretability — but the list must be defined **independent of the outcome** (a list derived from this data's own contrast leaks and is circular). When you cache such a run, put a **canonical (sorted, de-duplicated) `feature_list`** into the fingerprint `params` so the same feature set reuses one cache entry regardless of input order (`conventions/results-cache.md`). **Enrichment / pathway biology** — *what biology is my hit / selected list enriched for?* — is the natural **downstream** of feature finding/selection: seed from **`lib/analysis/enrichment`** (`enrich(query, background, organism=…)`, GO:BP/MF/CC + KEGG over-representation via g:Profiler) with the DE bridge **`enrich_from_differential_abundance(result, dataset, organism=…, direction="up"|"down")`** (enrich the up- and down-hits **separately** — far more interpretable), and render with **`lib/figures/enrichment`** (`enrichment_dotplot` / `enrichment_barplot` / `enrichment_manhattan` — offer the scientist the style). The **query** is any hit/selected list (DE hits, Boruta-confirmed, classifier-selected, a cluster); the **background** is the experiment's detected proteome (`dataset.feature_names`) — **not** the whole genome (which trivially inflates tissue-ubiquitous terms). **Before running, a hard Stage-4 checkpoint on the ID encoding:** g:Profiler needs UniProt accessions, so show the scientist the decoding via `build_mapping_audit` — per-source counts, mappable %, worked `original → accession` examples (e.g. `sp|A1L3T7|RIPR3_MOUSE → A1L3T7`), and the full **unmappable** list — and get **explicit sign-off**; if the scheme is unusual they supply a custom `id_parser=` (a one-function fix). Then confirm the **background** and **correction** (g:SCS default; fdr/bonferroni available). The result carries the **g:Profiler data version** (record it in provenance — a versioned live service is only reproducible against a stated release) and the **decode audit**; write the per-term table + the audit to CSV, embed the figure(s) in the finding, and `relates_to` the upstream discovery. Enrichment is a plain table (no CPU-heavy cache needed) but **does hit the network** — a service failure **raises** (`EnrichmentServiceError`), never a silent empty result.
2. **Go back and forth.** A plot looks interesting, a protein group invites a question, the scientist points at a heatmap cluster. Investigate by composing or writing analysis — held to the coding and statistical conventions (no bare p-values; effect size + CI + a named correction; report all tests run; no leakage; CV matched to the generalization target; label-shuffle null for classifiers; small-n is exploratory). Dispatch the **statistician**/**coder** and their reviewers where available.
3. **Capture every substantive insight as a finding — the moment it emerges.** Dispatch the **findings-manager** to record it. *What counts:* a tangible, specific, evidence-bearing observation — if it has an effect, a statistic, or a concrete claim someone might later cite, record it. **Bias toward capturing too much**; capture is cheap and low-bar (`candidate`). Give the scientist a brief, non-disruptive notice ("recorded as finding 0042"). Do not stop the flow to apply rigor — rigor is applied at promotion (Stage 5). **Show, don't tell — every claim that can be shown gets a figure.** Before recording, go claim by claim and ask **"what figure shows this?"** If the exploration already produced one (a volcano, a PCA re-render, a classifier ROC), it belongs *in* the finding, not merely in `figures/`; if it did not, **dispatch a `figure-generator` to make it**. Commissioning the figure is part of recording the claim, not a later tidy-up — the figure is how the claim is made. **Hand the findings-manager every figure the finding is about, with each figure's producing script + input** (path + commit, `data_version`, and the `result_id` when it was rendered from a cached result) **plus the generator's caption and reading**, so the finding embeds each figure inline *and explains it in the prose* — no one should have to track a figure down, or work out unaided what it shows (`conventions/findings.md` §2.4, §9). This does not stall the flow: if a figure will take a moment, record the `candidate` now and add it (listed, embedded, explained) as soon as it renders — the manager's **uncovered-claim flag** is what keeps it from being forgotten. A claim that genuinely cannot be shown (a bare count, a design fact) simply carries no figure.
4. **Keep the exploration log honest.** Append what was looked at and discarded to `findings/exploration-log.md` — this is the multiplicity context that informs each finding's caveats. Mark findings `exploratory` by default; confirmatory requires held-out/orthogonal data (Stage 5).

## Caching heavy results (compute once, re-render figures)

The CPU-heavy analyses — `classification`, `classification-xgboost`, `regression`, `boruta` (nested CV + the permutation **null**) — must not be re-run just to tweak a figure. Split them into a **compute script** and **figure scripts** (`conventions/results-cache.md`; substrate `lib/analysis/result-io`):

- **Before running, check the cache.** Fingerprint the requested analysis + `data_version` + params + seed (`result_fingerprint`) against `results/manifest.md`. **If that exact result already exists, reuse it** — don't silently recompute. Tell the scientist it exists; recompute only if they ask.
- **Compute → persist → register.** The compute script calls `save_cached_result(result, cache_root="results", analysis=…, data_version=…, params=…, seed=…, label=…)` (`params` must capture *every* knob that changes the numbers — `outcome`/`binarize`/`covariates`/`feature_list`/`run_null`/method/seed); dispatch the **findings-manager** to register the returned `ResultMeta` in `results/manifest.md`.
- **Figures load the cache.** Each result figure `load_cached_result(...)`s a **named** result (or the analysis's **current** one) and renders — a title/color tweak re-runs only the figure. Record the result id in the figure and in the finding's `provenance.result_id`.
- **Intent is explicit; keep-all is the default.** A **new** run with different params is a **new** result (the prior is marked `superseded`, kept — **never auto-deleted**). Ask before regenerating an existing result or pruning; a result a **finding references is protected**. When the scientist asks for a figure, they may **name** which cached result to visualize (default: `current`).

## Normalization & batch correction (analysis preprocessing)

Most analyses run on normalized, log-scale data, and some warrant batch correction. Both are recorded scientific choices — seed from the `lib/` templates and carry the decision into `provenance.params` (`conventions/statistics.md`):

- **Normalization** — seed from the `normalize` template; use the method confirmed in Stage 2 (median by default; MAD/VSN if the scientist chose them). The `scale` tag prevents double-logging.
- **Batch correction** — seed from `batch-correct-combat`. It is **batch-label-only** (never hand ComBat the covariate of interest — under confounding that launders a batch artifact into the signal under test). Before correcting: run `assess_batch_confounding`, surface the result, and get explicit scientist **sign-off** if a covariate of interest is confounded with batch. For *significance testing*, prefer modeling **batch as a covariate** in the differential design over pre-correcting (pre-corrected values inflate significance — variance deflation) — in the DE template this is just `covariates=["…batch…"]` (batch is a nuisance covariate, never the `contrast`); use ComBat output for visualization and the robustness check. Then **report the key analysis both corrected and uncorrected** — survival-of-correction is the robustness test (with the caveat that partial confounding attenuates real signal too). Run the template twice (uncorrected with batch-as-covariate, and on the ComBat-corrected matrix) and overlay the two p-value histograms; put the conclusion in the finding's caveats.

## Skepticism calibration

**Generous here.** Capture freely as candidates. A main agent that doubts everything in real time kills the exploration the system exists to capture. The ruthless skepticism lives at promotion (Stage 5), not at every breath.

## Provenance discipline (so findings stay regenerable)

Every finding's numbers must be regenerable: pin `data_version`, the script (path + commit), params, the locked environment, the template lineage (`seeded_from`), and any seed. A finding may be **promoted/validated only against a script in `scripts/promoted/`** — scratch work is fine for candidates, but promotion requires the script to pass tests/types/lint and move to `promoted/`.

## When candidates mature

Run `stage5-validate` to put a finding through independent validation. Validation runs continuously as candidates mature — you don't have to finish exploring first.

## Workflow state

`current_stage` is already **4** (set when the integrity gate passed); Stage 4 is the open exploration loop, so there is no `*_done` flag to set. Bump `state/workflow.json` `updated` as exploration proceeds so `status` reflects recent activity.
